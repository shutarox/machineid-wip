## インフラ(本番構成)

> 構成そのものの決定は `docs/decisions/20260806-aws-minimal-prod.md`。ここに残るのは、その構成を選んだ結果として**受け入れたまま先送りしたリスク**。

### 本番の論理バックアップが取れない(RDS の自動バックアップ 7 日のみ)

- 記録日: 2026-08-07
- 対象: インフラ(`prod/base` の RDS)/ `pgdump/pgdump.sh`

**症状**: 本番のバックアップは **RDS の自動バックアップだけ**。保持 7 日、PITR は約 5 分粒度で機能している(`LatestRestorableTime` が更新され続けていることを確認済み)。AWS Backup のプランは無い。

**`pgdump/pgdump.sh` はあるが、本番には使えない。** 定期実行になっていないという以前に、**手動でも取れない**。

1. **開発コンテナから RDS に届かない。** private サブネット・`publicly_accessible = false`・SG は `is_app`(ECS タスク)からの 5432 のみ。VPC の外に接続経路が無い
2. **コンテナの中で取っても持ち出せない。** ECS Exec で入れば `pg_dump` は動く(`postgresql-client-18` は同梱)が、**本番イメージに `aws` も `curl` も入っていない**(意図的に slim にしてある)ので、S3 にもどこにも送れない

`pgdump.sh` が現に動くのは**ローカル DB に対してのみ**で、2026-08-04 の修理もその経路のもの。「スクリプトがあるから本番も取れる」と読み違えやすい(実際に読み違えた)。

**影響**: 次の 2 つに対処できない。

- **7 日より前に戻したい**(誤削除や不正なマイグレーションに 1 週間以上気づかなかった場合)
- **アカウントやインスタンスごと失う事故**。RDS のスナップショットは同一アカウント・同一リージョンにあり、インスタンスに紐づく

日常の復旧は PITR のほうが速く確実なので、**論理バックアップが効くのはこの 2 つに限られる**。

**見送り理由**: PoC 期で**顧客データがまだ入っていない**ため。7 日 PITR で実用上足りる。

**対応するときの方針**: **`backend/script/db_backup.ts` を作る**(`pg_dump` を子プロセスで実行 → `@aws-sdk/client-s3` でアップロード。SDK は既に依存にある)。本番イメージに AWS CLI を足す案は、slim を保つ方針と衝突するので採らない。あわせて必要なもの:

- **バックアップ専用の S3 バケット**(アップロード画像と混ぜない)。ライフサイクルで保持期間を切る
- タスクロールにそのバケットへの `s3:PutObject`。S3 への到達は既設の Gateway エンドポイント経由
- 接続は `.pgpass`(appuser)が既にあるのでパスワードの受け渡しは不要

**作れば定期実行と手動実行が同じ仕組みになる** — `./deploy/run_task.sh 'node /app/backend/build/script/db_backup.js'` で任意のタイミング、EventBridge のルールを足せば定期(`39_scheduled_task.tf` の `cleanup_uploads` を写す)。頻度は週 1・保持 90 日程度で十分。

**着手の目安: 顧客データが入る前。** PoC を抜けるタイミングで再評価する。

### RDS が Single-AZ で、メンテナンスと障害時にダウンタイムが出る

- 記録日: 2026-08-06
- 対象: インフラ(`prod/base` の RDS)

**症状**: `multi_az = false` の単一インスタンス構成。マイナーバージョン更新などのメンテナンスウィンドウ中は数分の再起動が入り、AZ 障害やインスタンス障害では復旧に手動対応(スナップショットからのリストア)が要る。

**影響**: 障害時にサービス全断。復旧時間は数分〜数十分で、RPO はバックアップ間隔(自動バックアップ + トランザクションログで概ね 5 分)に依存する。

**見送り理由**: Multi-AZ にすると DB コストが倍(約 $32 → $64/月)になる。案件の初期段階で可用性 SLA の要件が定まっておらず、コスト最小化が優先されたため。

**対応するときの方針**: `multi_az = true` に変更する(**インスタンスタイプの変更を伴わないため、ダウンタイムはフェイルオーバー相当で済む**)。あわせて `backup_retention_period` の見直しも行う。可用性要件が出た時点で `20260806-aws-minimal-prod.md` に改定履歴を追記すること。

### presigned URL から AWS アカウント ID が露出する

- 記録日: 2026-08-06
- 対象: `backend/src/libs/storage.ts`(画像配信)

**症状**: 画像は S3 の presigned URL でブラウザに配信している。SigV4 は認証情報スコープをクエリ文字列に含めるため、URL に `X-Amz-Credential=ASIA.../20260806/ap-northeast-1/s3/aws4_request` が必ず現れる。**AWS のアクセスキー ID にはアカウント ID がエンコードされており、オフラインで復元できる**(`sts:GetAccessKeyInfo` という公式 API もある)。バケット名を工夫しても、この経路は塞がらない。

**影響**: アカウント ID は認証情報ではなく、単体で悪用できるものではない(AWS も「秘密ではないが公開は推奨しない」という位置づけ)。実害は偵察の足がかり — ロール名の推測、AWS サポートを騙るソーシャルエンジニアリング、confused deputy 系攻撃の前提条件。**presigned URL を露出している実運用サービスは一般的**であり、リスクは低〜中。

**見送り理由**: 塞ぐには CloudFront 経由の配信(署名付き URL / Cookie)へ移す必要があり、`libs/storage.ts` と表示側の変更を伴う。報告書の画像は**ロールで見える範囲が変わる**ため、アクセス制御の移植が小さくない。PoC 期に払うコストとして見合わない。

**対応するときの方針**: **CloudFront + OAC で画像専用のディストリビューションを立て、署名付き URL / Cookie に移す。** SPA 用の CloudFront はどのみち作るので追加は 1 つ。露出対策としてだけでなく、**キャッシュが効いて S3 のリクエスト課金とレイテンシが下がり、自社ドメインで配信できる**ので、配信アーキテクチャとしても上位互換。あわせて**画像バケット名にアカウント ID を入れない**(現行の命名を維持すること。tfstate バケットは URL に出ないので入れてよい)。

### `/api/ping` がテナント 0 件で 500 を返し、シード前の環境が起動できない

- 記録日: 2026-08-07
- 対象: `backend/src/routes/api/ping.GET.ts` / ALB のヘルスチェック

**症状**: `/api/ping` は DB 疎通確認として `tx.tenant.findFirst({})` を実行し、**結果が無いと `tenant not found` を投げる**。ALB のヘルスチェックがこのパスを見ているため、マイグレーション直後(データが空)の環境では**ターゲットが永久に unhealthy** になり、ECS がタスクの起動と停止を繰り返す。

**影響**: 新しい環境を立ち上げるとき、**シードを流すまでサービスが安定しない**。2026-08-07 の本番初期構築で実際に踏み、原因の切り分けに時間を要した(アプリのログは `listen...` まで正常に出るため、一見して原因が分からない)。

**見送り理由**: シードを流せば解消し、初期構築時にしか起きない。ヘルスチェックの意味を変える(疎通確認をどこまでとするか)判断を伴うため、初期構築の勢いでは決めない。

**対応するときの方針**: `findFirst` の結果が無くても **200 を返す**ようにする(接続できた時点で DB は生きている)。テーブルの存在確認までしたいなら `count` を使い、0 件を正常とする。**ヘルスチェックのパスを変えるのではなく `/api/ping` 側を直す** — メンテナンスモードの 200 応答(`docs/decisions/20260806-aws-minimal-prod.md` 関連)もこのルートに集約されているため。

### シードした管理者の初期パスワードが CloudWatch Logs に残る

- 記録日: 2026-08-07
- 対象: `backend/script/seed.ts`

**症状**: `seed.ts` は初期パスワードを標準出力に表示する。ローカルでは端末に出るだけだが、**ECS の run-task で流すと CloudWatch Logs に平文で残る**。

**影響**: ログ閲覧権限を持つ者が初期パスワードを読める。ログの保持期間は 30 日。**2026-08-07 の本番シードで実際に記録されている**。

**見送り理由**: 初回ログイン後にパスワードを変更すれば無効化される。ログの遡及削除より運用でカバーするほうが確実。

**対応するときの方針**: 初期パスワードを標準出力ではなく **SSM の SecureString に書き込む**(`/machineid-keys/INITIAL_ADMIN_PASSWORD` 等)か、パスワードを設定せず**初回のパスワード設定リンクを発行する**方式にする。当面は**本番でシードしたら管理者パスワードを変更する**運用とする。

### Slack 通知が設定されておらず、しかも**黙って握りつぶされている**

- 記録日: 2026-08-07
- 対象: `deploy/notify_slack.sh` / `docker/docker-compose.local.yml`
- **まっさら化の後に設定する**(この台帳は残るので、そこで拾う)

**症状**: `SLACK_WEBHOOK_URL` が実在する webhook になっていない。

- 開発コンテナには compose が**プレースホルダ**を入れている(`https://hooks.slack.com/services/***/***/***`)
- **本番の ECS タスク定義には入っていない**(アプリ側は使っておらず、使うのは `deploy/*.sh` だけ)

そして `notify_slack.sh` は**未設定のときだけスキップの旨を出す**作りなので、
プレースホルダが入っていると通知を試み、失敗を握りつぶす。

```
$ curl -s -o /dev/null -w "%{http_code}" -X POST ... "https://hooks.slack.com/services/***/***/***"
302   ← curl の終了コードは 0
```

`curl ... || echo "failed"` は **HTTP エラーでは発火しない**(トランスポート層の失敗だけ)。
結果として **「未設定」より悪い** — スキップの表示すら出ないので、通知が飛んでいないことに気づけない。
実際、今日のデプロイ 8 回はすべて無言で終わっている。

**影響**: デプロイ完了・**マイグレーション失敗**の通知が誰にも届かない。
`deploy_prod-main.sh` は migrate が失敗すると `notify_slack "... **migration failed** ..."` を出すが、
これも飛んでいない。**気づけないまま失敗する経路**になっている。

**見送り理由**: 運用者が実質 1 名で、デプロイは対話的に実行して結果を目で見ているため。

**監視 Lambda の側は配線済み**(2026-08-07)。`terraform/environments/prod/main-app/38_monitoring.tf`
の 2 つの Lambda は SSM の `/machineid-keys/SLACK_WEBHOOK_URL` を実行時に読み、
**未設定なら無送信で正常終了する**。つまりこの項目でやることは、Lambda については
「SSM にパラメータを 1 つ作る」だけになった(コード・terraform の変更は不要)。
`deploy/*.sh` 側は下記 2・3 が残っている。

**対応するときの方針**:

1. 実在する Incoming Webhook を作り、**SSM の SecureString**(`/<project>-keys/SLACK_WEBHOOK_URL`)に置く
   — compose に直書きすると雛形の履歴に残る(**過去に実際に webhook URL が履歴へ混入している**。
   `docs/plans/20260806-derive-first-project.md` の「秘密情報の混入」)
2. `deploy/*.sh` は実行時に SSM から取得する(`aws ssm get-parameter`)
3. **`notify_slack.sh` を「HTTP ステータスも見る」ように直す。** いまの実装は
   プレースホルダや失効した webhook を黙って見逃す。`-f`(`--fail`)を付けるか
   `%{http_code}` を検査し、2xx 以外なら警告を出す

**3 は雛形にも同じ問題があるので還元対象**(`docs/template-feedback.md`)。

### ECS Exec のセッションログを保存していない

- 記録日: 2026-08-06
- 対象: インフラ(`prod/main-app` の ECS クラスタ)

**症状**: `enable_execute_command = true` にするが、クラスタの `configuration.execute_command_configuration`(S3 / CloudWatch Logs へのセッションログ出力)は設定しない。

**影響**: 「誰が・いつ・どのタスクに」入ったかは CloudTrail の `ExecuteCommand` API 呼び出しで追えるが、**セッション内で実行したコマンドの中身は残らない**。本番 DB を触れる経路なので、監査要件が出た場合に遡れない。

**見送り理由**: 初期構成を簡素に保つため。ログ出力には S3 バケットか CloudWatch ロググループ、KMS 鍵(任意)の追加が要る。運用者が実質 1 名の段階では費用対効果が低い。

**対応するときの方針**: クラスタに `execute_command_configuration { logging = "OVERRIDE" }` を設定し、CloudWatch Logs のロググループへ出力する。**踏み台サーバを復活させる方向には戻さない**(`20260806-aws-minimal-prod.md` の「エージェント向けの注意」)。

### `pnpm dev` を上げたまま `pnpm verify` を回すとメモリのピークが高い

- 記録日: 2026-08-04(2026-08-04 更新: 実測に基づき vitest の並列度を制限)
- 対象: 開発コンテナ全体 / `backend/vitest.config.ts`

**症状**: `pnpm verify` の 4 段階のうち **`test` 段階だけ**メモリのピークが突出する。vitest の worker が 1 本あたり 400〜550MB 使うため。実際に `tsc --watch`(dev 側の型検査)が OOM で SIGKILL される事象が複数回発生した(cgroup の `oom_kill` は 20 まで増加)。

**実測**(dev 稼働中の anon ピーク。コンテナ全体は 7,836MB):

| 段階 | ピーク |
|---|---|
| 平常(dev のみ) | 2,716MB |
| `check` + `lint` | 4,759MB |
| `e2e` | 4,357MB |
| **`test`(worker 9 = 既定)** | **6,423MB(82%)** |
| **`test`(worker 4 = 現在)** | **4,655MB(59%)** |

**対応済み**: `vitest.config.ts` に `maxWorkers: 4` を設定した。`pnpm verify` 全体で測ると **時間は悪化せず(むしろ競合が減って速い)、ピークが既定比で約 1,750MB 下がる**。なお **`maxWorkers` を明示すると CPU 由来の既定を上書きする**ため、2 コアの CI も 1 本 → 4 本になる(実測)。verify の所要時間への影響はノイズの範囲(1 本 70/70/88/88s vs 4 本 78/82s)。

ピークは概ね `平常 2,716MB + N × worker 単価(現在 約 470MB)` で、**N は単価に掛かる係数**。アプリが育つと単価が上がるため、N を小さくしておく効果は成長に比例して大きくなる(単価が倍になると 6 では上限 7,836MB を超える)。

**残っている問題**: ピークは 59% で、余裕は約 3.2GB。他の重いプロセスが同時に走れば OOM は起こり得る。起きた場合の影響は「dev が約 7 秒不通になり、その間に E2E がリクエストすると落ちる」= **変更と無関係に verify が赤くなる**こと。dev-watch.sh の監視で自動復帰はする(ADR `20260804-dev-server.md`)。

**さらに対応するときの方針**: (1) 開発コンテナのメモリ割り当てを増やす(リポジトリ外)、(2) `pnpm verify` の前に `pnpm stop` する運用 — **ただし実測ではピークが 403MB しか下がらない**ので費用対効果は低い、(3) `maxWorkers` をさらに下げる(3 以下は実時間が伸び始める)。

> (2) の但し書きにあった「Playwright がバックエンドを自前起動する分 verify が延びる」は解消済み。**E2E は presigned URL のホスト名が dev と異なるため、常に専用ポート 8082 で自前起動する**ようになった(PR #44、経緯は `docs/decisions/20260805-file-upload.md`)ので、dev を止めても追加コストは発生しない。

### `CLAUDE.md` / `docs/` が雛形の視点のまま(案件化が未実施)

- 記録日: 2026-08-07
- 対象: `CLAUDE.md` / `README.md` / `docs/`

**症状**: 文章が「この雛形は〜」「案件で使うときは〜」という**雛形(`myapp`)としての視点**で書かれている。

**なぜ残っているか**: 当初はまっさら化の前に片付ける予定だったが、**雛形を `machineid` から作り直す方針**

**影響**: 初期コミットに雛形視点の文章が残る。エージェントが `CLAUDE.md` を読んだとき、
**このリポジトリを雛形だと解釈しうる**のが実害。

**対応するときの方針**: `myapp` を起こしたあとに `machineid` 側だけで書き換える。
少なくとも `CLAUDE.md` 冒頭の「プロジェクト概要」「現在のフェーズ」節と `README.md` は、
**まっさら化の直後に**直す(この 2 つは入口なので、放置すると誤解が固定する)。
