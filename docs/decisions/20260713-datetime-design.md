# ADR: 日時はワイヤー上 JST 正準形の文字列で貫き、自動 Date 変換をしない

- 状態: **採用**(2026-07-13、3c / 2026-08-03、3d で完成)
- 関連: `docs/plans/20260803-tanstack-query-plan.md` §4、`backend/src/libs/zDate.ts`(ルートスキーマの入口)

## 背景

日時は「どの層でどの表現なのか」が曖昧になると、ずれてもサイレントに壊れる。旧実装は 2 つの暗黙変換を抱えていた。

- サーバ側: MySQL 時代の名残で `+9h` を一律に足す処理
- クライアント側: `convertToDate` が生成 JSON スキーマを**実行時に参照**してレスポンスを in-place で書き換え、`date-time` フィールドを `Date` にしていた

後者は「型(`Date`)と実体の一致が生成物 2 系統の同期に依存し、壊れてもサイレント」という構造で、エージェントが静的に波及を追跡できない。

## 決定

### 1. ワイヤー表現は JST 正準形の ISO 文字列に固定する

**常に `+09:00` オフセット付き・秒精度**。`Z` 表記は使わない。オフセットなしの文字列は入力として拒否する。

```
2026-01-02T03:04:05+09:00
```

### 2. レスポンスの日時は string のまま扱う(自動変換をしない)

`convertToDate` と、そのために生成していた `openapi-schema.json` を**廃止**した。フロントエンドは日時を string として受け取り、**必要な箇所で明示的に `new Date()` する**。

### 3. 入出力は `zDateIn()` / `zDateOut()` に集約する

`backend/src/libs/zDate.ts`。

| ヘルパー | 役割 |
|---|---|
| `zDateIn()` | 入力。オフセット付き ISO 文字列 or 日付のみ → `Date`。**オフセットなしは拒否** |
| `zDateOut()` | 出力。`Date` のまま返し、シリアライズ時に replacer が正準形へ |

### 4. プロセスは JST で動かし、起動時に assert する

`TZ=Asia/Tokyo` を前提に置き、**起動時に検証して違えば落とす**。日時処理(`@db.Date` 正規化・JST シリアライズ)がこの前提の上に成り立っているため。

### 5. DB の型ごとの扱い

| 型 | 扱い |
|---|---|
| `DateTime` | `@db.Timestamptz(3)` で保存。レスポンスは replacer が `+09:00` 付き ISO 文字列に |
| `@db.Date` | PostgreSQL の `date` は TZ を持たないため、**入力時に JST の年月日を UTC 同日へ変換、出力時に UTC midnight を JST midnight へ補正**。カラム名は `date` のみ許可し、起動時にスキーマを検証する |

### 6. フロントエンドの日付ユーティリティ

`frontend/src/libs/dateParts.ts` はローカル時刻の年月日で扱い、**`Date.toISOString()` を使わない**。JST のブラウザで使うと 09:00 未満が前日にずれるため。

## 検証

- `zDateIn()` / `zDateOut()` の単体テスト
- `test/integration/framework/dbDate.test.ts` が `@db.Date` の正規化を固定
- 3a で Prisma 7 の driver adapter に対し **`@db.Date` の文字列パススルーは不可**と確認済み(pg の型パーサを identity にしても query compiler が `Date` へ再変換し、TZ ずれも健在)。**正規化拡張は温存が確定**

## 却下した選択肢

3d で「レスポンスを `Date` 型で受ける自動変換」を 2 方式検討し、いずれも棄却した(**蒸し返し不要**)。

- **スキーマ駆動**(旧 `convertToDate` 方式の温存): `openapi-schema.json` と手書きウォーカーの同期問題。`anyOf` / `$ref` 非対応で、ずれてもサイレント。テストのオラクル問題もある
- **パターン駆動**(値が正準形に全文一致したら `Date` 化): 自由入力文字列がたまたま正準形だった場合の偽陽性を原理的に排除できない。排除するにはフィールド命名規約 + 起動時検証が要り、雛形が複雑になる

**string 貫通 + 使用箇所で `new Date()`** が最もシンプルで、型と実体が常に一致する。

## エージェント向けの注意

- レスポンスの日時を「使いやすくするため」に **`Date` へ自動変換する仕組みを再導入しないこと**。上記のとおり 2 方式とも検討済みで棄却されている
- 日時のスキーマを書くときは `z.date()` / `z.string()` を直接使わず、**`zDateIn()` / `zDateOut()` を使う**
- `toISOString()` は UTC 変換なので、日付だけを扱う場面では使わない
