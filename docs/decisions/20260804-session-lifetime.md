# ADR: セッションはアイドル失効 + 延長方式とし、絶対失効は雛形に入れない

- 状態: **採用**(2026-08-04)
- 対象: `backend/src/config.ts`(`SESSION_IDLE_TIMEOUT_MS`)、`backend/src/plugins/sessionRetrieve.ts`
- 関連: `docs/decisions/20260804-security-headers.md`

## 背景

セッションクッキーの `expires` が **10 年固定**で、しかも**プロセス起動時に 1 回だけ計算**されていた(`docs/known-issues.md` に記録していた項目)。

調べたところ、実態はもっとずれていた。

- サーバ側は `lastActiveAt` による**無操作 10 分**の失効を持ち、超えると `401` + `actions: ['forceLogout']` を返してクッキーを消す
- つまり**クッキーの寿命(10 年)と実際のセッション寿命(10 分)が約 52 万倍ずれていた**
- さらに 10 年という値はそもそも尊重されない。**Chromium は Cookie の寿命を 400 日で切り詰める**

加えて、当初この 10 分は「**盗まれたセッションキーを延命して使い続けられないようにする**」目的で置かれていたが、**その目的は達成されていなかった**。`lastActiveAt` は**攻撃者自身のリクエストでも更新される**ため、攻撃者が閾値より短い間隔でアクセスし続ければ無期限に延命できる。アイドル失効が守るのは「正規ユーザが離席し、攻撃者も使っていないセッション」だけである。

## 決定

**アイドル失効 + 活動による延長**という方式を採る。**絶対失効(セッション開始からの上限)は雛形に入れない。**

- **`SESSION_IDLE_TIMEOUT_MS` = 7 日**(雛形の既定)。この 1 つの定数から、**サーバ側の失効判定とセッションクッキーの `maxAge` の両方**が導かれる
- **`SESSION_TOUCH_INTERVAL_MS` = 1 時間**。`lastActiveAt` の更新とクッキーの再発行を間引く間隔。失効までの猶予に対して十分小さければよい
- クッキーは `expires` をやめて **`maxAge`** にする。`expires` はプロセス起動時に確定するが、`maxAge` は**ブラウザが受信時に計算する**ため、長寿命プロセスでもずれない
- **`lastActiveAt` を更新する場所で、セッションクッキーも必ず一緒に再発行する。** サーバだけが延命してクッキーが放置される非対称を作らない

### クッキーの options を 2 つに分ける

`DEFAULT_COOKIE_OPTIONS` は `sessionId` だけでなく **`deviceId` からも使われている**。`deviceId` は端末をセッション横断で識別する主体なので、セッションと同じ寿命にしてはいけない(短命にすると次のリクエストで新しい deviceId が発行され、ログインが `upsert({ where: { deviceId } })` である以上、**古い `LoginSession` 行が孤児として残り「1 端末 1 セッション」が崩れる**)。

| options | 用途 | `maxAge` |
|---|---|---|
| `DEFAULT_COOKIE_OPTIONS` | `deviceId` など | 400 日(Chromium の上限に合わせる) |
| `SESSION_COOKIE_OPTIONS` | `sessionId` | `SESSION_IDLE_TIMEOUT_MS` |

## この決定が守らないこと(重要)

**盗まれたセッションキーの無期限の延命は防げない。** 攻撃者が 7 日以内の間隔でアクセスし続ければセッションは生き続ける。これは**意図的に受け入れた制約**であり、実装漏れではない。

現状の緩和策は**デバイス束縛**である。セッションの照合は `where: { sessionId, deviceId }` で、**2 つのクッキーが揃わないと通らない**。どちらも `httpOnly` + `secure` + `sameSite: 'strict'` + 署名付きなので、XSS で `document.cookie` から読み出すことはできない。

## 却下した選択肢

- **絶対失効(`sessionStartedAt` からの上限)を入れる**: 盗まれた鍵の延命を実際に止められる唯一の手段だが、**正規ユーザも上限で必ず再ログインになる**。雛形の既定として押し付ける性質のものではなく、要件によって妥当な値が大きく変わる(シフト運用なら 12 時間、SaaS なら 30 日)。**必要な案件が足す**方針とした。実装するなら `createdAt` は使えない点に注意 — ログインは `upsert({ where: { deviceId } })` で行を再利用するため、`createdAt` は「その端末の初回ログイン」を指す。**専用のカラムを足す必要がある**
- **セッションクッキー(`maxAge` なし、ブラウザ終了で消える)にする**: 最も安全側だが、ブラウザを閉じただけで再ログインになる。雛形の既定としては厳しすぎる
- **クッキーを長寿命のまま残す**(現状維持): サーバが 401 で弾くので実害は小さいが、**寿命の情報源が 2 か所に分かれたまま**になり、どちらが効いているのか読み取れない

## エージェント向けの注意

- **セッション寿命を変えるときは `SESSION_IDLE_TIMEOUT_MS` だけを変える。** サーバ側の判定とクッキーの `maxAge` は両方ここから導かれている。片方だけ直す変更を入れない
- **絶対失効を「セキュリティ強化」として勝手に追加しないこと。** 上記のとおり**意図的に外している**。追加するなら、この ADR に改定履歴を書いてから実装する
- **`expires` に戻さないこと。** プロセス起動時に 1 回だけ計算される実装は、長寿命プロセスで寿命がずれる
- **`sessionId` に `DEFAULT_COOKIE_OPTIONS` を使わないこと。** `SESSION_COOKIE_OPTIONS` を使う。逆に `deviceId` にセッション用を使うと「1 端末 1 セッション」が崩れる
- 挙動は `backend/test/integration/framework/sessionLifetime.test.ts` が固定している(失効 / 延長 / 再発行の間引き / `maxAge` の一致)
