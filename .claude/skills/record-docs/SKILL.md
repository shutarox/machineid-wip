# 計画・決定・保留を docs に残す

**4 つに振り分ける。** どれにも当てはまらない口頭の指摘は、次のセッションに残らないものと考える。

| 種類 | 置き場所 | いつ書くか |
|---|---|---|
| **計画** | `docs/plans/YYYYMMDD-<slug>.md` | まとまった作業の**着手前**(ブランチ/PR の単位と対応させる) |
| **決定** | `docs/decisions/YYYYMMDD-<slug>.md`(ADR) | 方針を決めた・変えたとき |
| **保留** | `docs/known-issues.md` | 問題を見つけたが**その場では直さない**と判断したとき |
| **雛形への還元** | `docs/template-feedback.md` | **このプロジェクト固有ではなく、雛形(`myapp`)側の問題**だと分かったとき |

判断の分かれ目:

- **「対応しないことに決めた」なら保留ではなく決定**(ADR)に書く
- **「この案件でどう直すか」は保留、「雛形をどう直すか」は還元。** 両方に該当することもある
  (このリポジトリで直しつつ、同じ差分を雛形へ持っていく)

## 計画(`docs/plans/`)

着手前に実装計画を書く。実施後に判明した逸脱や訂正は**同じファイルに追記**する(新しいファイルを作らない)。

## 決定(`docs/decisions/` = ADR)

### 書くべき場面

- ライブラリやスタックの選定
- 既存方針の変更
- 複数案を比較して 1 つを採ったとき
- 「なぜこうなっているか」が後から疑問になりそうなとき

### 必ず含める 4 点

```markdown
# ADR: <決定を一文で>

- 状態: **採用**(YYYY-MM-DD)

## 背景
## 決定
### 根拠
## 却下した選択肢
## エージェント向けの注意
```

**「却下した選択肢」と「エージェント向けの注意」が本体。** これが将来の逆行提案(モックの追加、独自抽象の再導入、削除済みライブラリの復活など)を止める。

### ファイル名と改定

- 日付は **決定日**(書いた日ではない)
- **改定してもリネームしない。** 参照が壊れ、決定日の意味も失われる。方針を変えたら本文に**改定履歴**を追記する
- 索引 `docs/decisions/README.md` の一覧にも行を追加する
- **既存 ADR に反する変更をするときは、実装より先に ADR を更新する。** ADR とコードが食い違った状態を残さない

## 雛形への還元(`docs/template-feedback.md`)

**派生側の git 履歴は捨てるので、書き残さないと `myapp` に戻せない。**
この台帳は**まっさら化(git 履歴のリセット)後も残す** — 還元は 1 回で終わらず、
案件を進めるほど雛形の穴が見つかるため。

- **何が起きるか**を先に書く(「〜が無い」ではなく「〜すると壊れる」)
- **ローカルでは踏めない類か**を書く(本番でしか出ない問題は、書かないと二度と気づけない)
- このリポジトリで既に直したなら**その旨と差分の在り処**を書く(そのまま持っていける)
- **`myapp` に反映したら一覧から削除する**(履歴は git に残る)

判断に迷ったら足す。消すのは簡単だが、思い出すのは難しい。

## 保留(`docs/known-issues.md`)

### 各項目に必ず書く 4 点

```markdown
### <症状を一文で>

- 記録日: YYYY-MM-DD
- 対象: <ファイル / 領域>

**症状**:
**影響**:
**見送り理由**:
**対応するときの方針**:
```

**「なぜ直さないのか」が無いと、後で見た人が同じ調査をやり直すことになる。**

### 運用

- **対応したら一覧から削除する**(履歴は git に残る)。放置された項目が積み上がると台帳自体が信用されなくなる
- 既存項目に関係する作業をするときは、**着手前に該当項目を読む**(前提が変わっていることがある)
